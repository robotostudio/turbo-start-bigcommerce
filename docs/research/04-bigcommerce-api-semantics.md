## LEAD FINDING — the standard SSR token pattern is on a sunset clock

The classic pattern (mint a token at `POST /v3/storefront/api-token`, call GraphQL from the server) is
deprecated. The unambiguous sentence:

> "Storefront tokens used in server-to-server contexts are deprecated. Use private tokens for
> server-to-server and headless interactions instead."
— https://docs.bigcommerce.com/developer/docs/storefront/guides/graphql-storefront-api/authentication

The same page carries **two** dated deprecations that share the same dates, and I extracted both verbatim
on separate reads. Reporting both because they do not say the same thing:

| Quote | Reading |
|---|---|
| "Storefront tokens created after June 30th, 2026 will no longer support server-to-server (s2s) use." / "…created on or before June 30th, 2026 will continue to support s2s calls until March 31st, 2027." | s2s cutoff |
| "**June 30, 2026**: Storefront tokens can no longer be created without `allowed_cors_origins`." / "**March 31, 2027**: Storefront tokens without `allowed_cors_origins` will no longer be accepted for API requests." | CORS-origin requirement |

**What is safe to act on:** hard stop **March 31, 2027** either way. Use `POST /v3/storefront/api-token-private`
for anything server-side, and always set `allowed_cors_origins` on browser tokens.
**NOT verified:** whether a vanilla token minted today already fails from a server. I did not test it, and
the two quotes disagree on that point. The recommendation below is unchanged either way.

Practical consequence: BC+Next.js tutorials written before 2026 show the vanilla-token-for-SSR pattern,
which is on its way out. Don't copy them.

# Q1 — CHECKOUT

## The four options that actually exist

### 1. Redirected (hosted) checkout — the Shopify `checkoutUrl` analogue
- **Yes, there is a one-line equivalent.** Generated by either:
  - GraphQL: `mutation { cart { createCartRedirectUrls(input: {cartEntityId: "..."}) { redirectUrls { embeddedCheckoutUrl redirectedCheckoutUrl } } } }`
    — https://docs.bigcommerce.com/developer/docs/admin/checkout-and-cart/custom-checkouts/graphql-storefront
  - REST: `POST /stores/{store_hash}/v3/carts/{cart_id}/redirect_urls`, or `POST /v3/carts?include=redirect_urls`
    → `redirect_urls { cart_url, checkout_url, embedded_checkout_url }`
    — https://docs.bigcommerce.com/developer/docs/storefront/headless/cart-and-checkout/checkout
- **Auth**: GraphQL variant needs only a Storefront token. "To make requests, create a store-level API account
  with one or more of the following token creation OAuth scopes: Storefront API Tokens or Storefront API
  Customer Impersonation Tokens." / "No additional scopes are required to use the GraphQL Storefront API"
  → **no OAuth/X-Auth-Token REST client needed in the happy path.**
  REST variant needs server OAuth `X-Auth-Token`.
- **CRITICAL DIVERGENCE FROM SHOPIFY — single use:**
  > "Each cart redirect URL may only be used once. Once a redirect URL has been visited, it will be invalidated and cannot be used again."
  > "If your application requires URLs to be visited more than once, consider generating a fresh one each time you need to restore a cart."
  — https://docs.bigcommerce.com/developer/learn/courses/checkout-orders-rest-api/management-api/cart
  **You cannot cache `checkoutUrl` on the cart object Shopify-style. Mint fresh on every click.**
- **URL bar**: BigCommerce-controlled domain, but you set it — the channel's site checkout URL.
  "You need a primary domain name for your headless storefront and an additional domain for the storefront's
  checkout page." / "Subdomains are permitted."
  — https://docs.bigcommerce.com/developer/docs/storefront/headless/channels
  So `www.mystore.com` → `checkout.mystore.com`. Not a `*.mybigcommerce.com` URL if configured.
- **BC owns**: payments, PCI, tax, shipping calc, order creation. **You own**: nothing after redirect.
- **Plan**: none stated. This is what BC's own Catalyst uses:
  "Catalyst uses Redirected Checkout out of the box" / "Redirected Checkout does NOT require a separate
  Stencil channel." / "When a single Catalyst storefront is needed, Multi-Storefront (MSF) does NOT need to be enabled."
  — https://docs.bigcommerce.com/developer/docs/storefront/catalyst/getting-started/overview

### 2. Embedded checkout (iframe on your domain)
- SDK method `embedCheckout({ containerId, url })` using `embedded_checkout_url`.
- Sequence: `POST /v3/channels` → `POST /v3/channels/{id}/site` → `POST /v3/carts` → `POST /v3/carts/{id}/redirect_urls`
- Scopes: Carts modify, Channel Settings modify, Sites & Routes modify, Products read-only.
- **Blockers:** "At this time, you cannot embed a checkout that uses a hosted payment gateway."
  "For Embedded Checkout to work correctly for shoppers using a browser with restricted privacy settings,
   like Apple's Safari, your checkout page must be served from the same domain as your BigCommerce storefront."
  — https://docs.bigcommerce.com/developer/docs/admin/checkout-and-cart/embedded-checkout/tutorial
- **Plan**: no tier named on any of 7 first-party pages checked. Historically believed Enterprise-only. UNVERIFIED either way.
- URL bar: your domain. BC owns the iframe contents + PCI.

### 3. Fully headless GraphQL checkout
- Mutations: `getCheckout` (via `site.checkout`), `addCheckoutBillingAddress`,
  `addCheckoutShippingConsignments`, `selectCheckoutShippingOption`, `completeCheckout`
- **Hard stop:** "For PCI compliance-related reasons, the GraphQL Storefront API does not handle payments."
  → must use the separate Payments API (50 req/4s). You take on PCI scope.
- Also unsupported: "File upload product options, *Buy Online, Pick up in Store*, Checkout directly from
  the Product Details Page, or *Buy Now* carts."
  — https://docs.bigcommerce.com/developer/docs/admin/checkout-and-cart/custom-checkouts/graphql-storefront

### 4. Open Checkout (fork `checkout-js`)
- Fork → build `/dist` → host it (S3 etc.) → set loader URL in Checkout Settings > Custom Checkout > Script URL
- Node >= 22, npm >= 10. PCI DSS 4.0 needs checkout-js >= 1.548.2.
- You own the checkout UI + its PCI compliance + you lose automatic updates. Still runs on BC's checkout domain.
- https://github.com/bigcommerce/checkout-js

## Options for our starter
| Option | Trade-off |
|---|---|
| **A. Redirected checkout via `createCartRedirectUrls`** ← **RECOMMENDED** | Closest to the Shopify `redirect(cart.checkoutUrl)` you're mirroring; zero PCI; pure GraphQL so no second auth system. Only real cost: mint the URL on click, never cache it. |
| B. Embedded checkout iframe | Keeps shoppers on your domain, but breaks with hosted gateways, needs same-domain setup for Safari/ITP, and possible Enterprise gate is unverified — bad default for an OSS starter. |
| C. Fully headless GraphQL checkout + Payments API | Total UI control, but you inherit PCI scope and lose BOPIS/file-upload options. Wrong trade for a starter. |

**Pick A.** It's what BigCommerce's own Next.js framework ships. Leave B as a documented swap point.

# Q2 — STOREFRONT TOKEN LIFECYCLE

**Three token types.** All minted server-side with a store-level API account (`X-Auth-Token`).

| Token | Endpoint | Public-safe? | Purpose |
|---|---|---|---|
| Vanilla/public | `POST /v3/storefront/api-token` | **Yes** | Browser only (post-June-2026) |
| **Private** | `POST /v3/storefront/api-token-private` | **NO** | Server-to-server / SSR |
| Customer impersonation | `POST /v3/storefront/api-token-customer-impersonation` | **NO** | Legacy; being phased out |

- Vanilla: "Generally speaking, vanilla storefront tokens are not considered sensitive, and it is safe to
  expose them in web browsers." Fields: `channel_ids`, `expires_at` (required), `allowed_cors_origins`
  ("Currently accepts a maximum of two domains per created token").
  Deadline: "**March 31, 2027**: Storefront tokens without `allowed_cors_origins` will no longer be accepted."
- Private: "Private tokens are sensitive and should never be exposed publicly."
  "The API will reject private token-authenticated requests that originate from web browsers."
  `scopes` **required**, "one or more of: 'Unauthenticated', 'Customer', 'B2B'" → **one token can hold both**
  `["Unauthenticated","Customer"]`. One of `channel_id`/`channel_ids` required.
  Example body: `{ "channel_ids": [1,2,3], "expires_at": 1602288000, "scopes": ["Unauthenticated"] }`
  - `Unauthenticated` = "Query information from the perspective of an anonymous shopper."
  - `Customer` = "Access customer-specific data... You must pass the `X-Bc-Customer-Access-Token` header along with the private token."
- Impersonation: header `X-Bc-Customer-Id`. "Unless your frontend client proxies requests, attempts to
  authenticate from the browser using customer impersonation tokens will be rejected."
  Described as "less secure than customer access tokens and are being phased out for sensitive features."

**Expiry/TTL:** `expires_at` is a required Unix timestamp. **No documented maximum on either endpoint.**
> "As a best practice, you should create tokens that expire and rotate them regularly before their expiry.
> However, you are also permitted to create long-lived tokens."

**Scopes needed on the API account** (https://docs.bigcommerce.com/developer/docs/overview/api-fundamentals/api-accounts):
`store_storefront_api` ("Create GraphQL Storefront API bearer tokens"),
`store_storefront_api_customer_impersonation`.
The store-level OAuth token itself: "access tokens do not expire based on time and cannot be manually invalidated."

**What a Next.js app must do:** nothing at runtime if you mint one long-lived private token out-of-band and
put it in env. **There is no refresh endpoint — you re-mint.** Don't build a refresh loop for a token whose
expiry you chose yourself.

**Starter default to pick (docs give no maximum, so this is our call):** mint the private token with
`expires_at` = **now + 1 year**, and put the re-mint command in the setup script + a note in the README.
Rotation is a manual, annual, out-of-band step. If you'd rather never think about it, the docs explicitly
permit long-lived tokens — but a dated token that you rotate beats an immortal secret in a public repo's
`.env.example`.

## Options for our starter
| Option | Trade-off |
|---|---|
| **A. One long-lived private token (`["Unauthenticated","Customer"]`) in env, all GraphQL server-side** ← **RECOMMENDED** | Simplest; one secret; survives the s2s sunset; client components hit route handlers/server actions. Cost: no direct browser→BC calls. |
| B. Mint both — private for SSR + vanilla with CORS origins for browser | Enables client-side queries without a proxy, but two secrets, two rotation paths, and CORS is capped at 2 domains (painful with Vercel preview URLs). |
| C. Runtime token minting with a cache | Auto-rotates, but adds a mint endpoint, a cache, and a failure mode, to solve an expiry you control. YAGNI. |

**Pick A.** The 2-domain CORS cap alone makes B hostile to preview deployments.

# Q3 — GRAPHQL STOREFRONT vs REST

BigCommerce has **four** GraphQL APIs — Account, Admin, Storefront, B2B
(https://docs.bigcommerce.com/developer/api-reference/graphql/overview).

## Capability → API → Auth

| Capability | API | Auth |
|---|---|---|
| Product / category / brand reads (storefront) | GraphQL Storefront `site.product`, `site.products`, `site.categoryTree`, `site.route()`, `site.popularBrands` | Storefront token (private for SSR) |
| Cart create/mutate | GraphQL Storefront `createCart`, `addCartLineItems`, `updateCartLineItem`, `deleteCartLineItem`, `deleteCart` | Storefront token |
| Checkout redirect URL | GraphQL Storefront `createCartRedirectUrls` | Storefront token |
| Checkout data (addresses, shipping) | GraphQL Storefront `addCheckoutBillingAddress` etc. | Storefront token + customer access token |
| **Payments** | **REST Payments API** — GraphQL explicitly excluded for PCI | Payments access token |
| Customer login/register/addresses | GraphQL Storefront `login`, `logout`, `registerCustomer`, `changePassword`, `requestResetPassword`, `resetPassword` | Storefront token |
| **Catalog WRITES** (create/update products) | **REST Catalog v3** `/v3/catalog/products` or GraphQL Admin | Server OAuth `X-Auth-Token` |
| **Channels / Sites / Routes** | **REST Management** `/v3/channels`, `/v3/channels/{id}/site` | Server OAuth `X-Auth-Token` |
| **Webhooks** | **REST Management** `POST /v3/hooks` | Server OAuth (no extra scope) |
| **Token minting** | **REST Management** `/v3/storefront/api-token*` | Server OAuth + `store_storefront_api` |
| Orders (admin) | REST Management v2/v3 | Server OAuth |
| Bulk catalog sync | REST `/v3/catalog/products?date_modified:min=` | Server OAuth |

**GraphQL Storefront explicitly does NOT cover:** payments; file-upload product options; BOPIS;
checkout from PDP; Buy Now carts; sorting by Price List pricing; public wishlists are read-only.
"Stores using BigCommerce's legacy Blueprint theme framework do not support the GraphQL Storefront API."

**Trap — REST Storefront API (`/api/storefront/*`) is unusable from Next.js.**
The API index lists its auth as "Same-origin CORS authentication", context "storefront".
"The REST Storefront API uses CORS headers for authentication... you do not need to send any
BigCommerce-specific tokens with your requests to these endpoints."
— https://docs.bigcommerce.com/developer/api-reference/about-our-apis
It relies on the BC session cookie on the BC domain. **Do not use it. Use `/v3/carts` or GraphQL.**

**Search caveat:** `site.products` / `site.product` are documented; a dedicated faceted-search root field
was **not** confirmed on the products guide page. The overview claims "searching, filtering, and sorting"
but names no query. **Partly UNVERIFIED** — check the GraphQL playground schema.

## Options for our starter
| Option | Trade-off |
|---|---|
| **A. GraphQL Storefront for 100% of the shopper path; REST Management only in build/sync scripts** ← **RECOMMENDED** | One typed client for the app; REST confined to the Sanity sync + one-time channel setup. Matches Catalyst. |

| B. GraphQL for reads, REST `/v3/carts` for cart | Slightly more documented examples exist for REST carts, but forces an OAuth client into the request path and a second auth model. |
| C. Route everything through REST Management | Maximum feature coverage, but you hand-roll typing, hit the 150–450 req/30s plan quota with shopper traffic, and diverge from BC's own reference. |

**Pick A.** Keeps the shopper path on the complexity budget rather than the request quota — see rate limits.

**You still need a server OAuth API account — but only twice, never on the request path:**
(1) minting the private token (`store_storefront_api` scope), (2) one-time channel/site/checkout-URL setup.
Plus the Sanity sync worker. So the starter needs a `BIGCOMMERCE_ACCESS_TOKEN` in setup scripts even though
no shopper request ever uses it. Don't let "GraphQL for everything" read as "no OAuth account needed."

# Q4 — CART

- **Created via GraphQL** `createCart` → returns `entityId` (a UUID). Mutations: `addCartLineItems`,
  `updateCartLineItem`, `deleteCartLineItem`, `deleteCart`, `createCartMetafield`.
- REST equivalent exists: `POST /v3/carts` (Management, server OAuth). `/api/storefront/carts` is the trap.
- **Cart ID lives in YOUR cookie on YOUR domain.** BC does not hold a session for your Next.js app.
  Catalyst's documented pattern: "attempt `addCartLineItem` if the user has a `cartId` cookie, and if no
  `cartId` cookie exists or the attempt fails, use `createCart`."
- **The handoff token IS the redirect URL.** `createCartRedirectUrls` returns a single-use URL; visiting it
  is what establishes BC's session on the checkout domain. There is no separate handoff token to manage.
- **Across the domain change:** the cart survives because it lives server-side at BC keyed by `entityId` —
  your cookie only holds the pointer. Customer identity also survives **if** you call
  `createCartRedirectUrls` with the customer access token: it "takes the current customer access token
  into account" — https://docs.bigcommerce.com/developer/learn/courses/catalyst-core/expanded/customer-session
  There is also `generateSessionSyncJwt` (args `redirectTo!`, `cartId`, `paymentWalletData`, `analytics`)
  for explicit session transfer. *(mutation signature from the GraphQL reference index — the dedicated
  session-syncing guide page does NOT document it; treat the arg list as lower-confidence.)*
- REST-created carts: "If you passed a `customer_id` in the Create a cart request, send the customer to a
  sign-in page before redirecting them to cart or checkout pages."
  — https://docs.bigcommerce.com/developer/docs/storefront/headless/cart-and-checkout/carts

## Options for our starter
| Option | Trade-off |
|---|---|
| **A. GraphQL cart, `cartId` in an httpOnly cookie, redirect URL minted on click** ← **RECOMMENDED** | Mirrors the Shopify starter's shape almost exactly; single-use URL handled correctly; identity carries free via the customer access token. |
| B. Same, but cache the redirect URL on the cart | One less round-trip — and it breaks on the second click, because the URL is single-use. Don't. |
| C. REST `/v3/carts` for cart ops | More examples online, but pulls server OAuth into every add-to-cart and burns plan quota per shopper action. |

**Pick A.** B is the trap the docs warn about explicitly.

# Q5 — CUSTOMER AUTH / SESSION

**Headless representation = customer access token.**
- `login` mutation → `customerAccessToken { value, expiresAt }`. Send as `X-Bc-Customer-Access-Token`.
- `logout` mutation invalidates it. "A customer access token becomes invalid on all devices when you log
  out of a single device." And: "A customer can only sign in on one device" — signing in elsewhere
  signs out the previous session. **This is a real UX constraint; surface it.**
- Recommended pairing: "use a **private token** with a customer access token" — i.e. private token
  (scope `Customer`) + `X-Bc-Customer-Access-Token`.
- Other mutations: `registerCustomer`, `updateCustomer`, `addCustomerAddress`, `updateCustomerAddress`,
  `deleteCustomerAddress`, `changePassword`, `requestResetPassword`, `resetPassword`.

**Customer Login API (JWT SSO)** — the bridge to BC-hosted pages.
`GET https://storedomain.com/login/token/{token}`. Claims: `iss` (client id), `iat`, `jti`,
`operation: "customer_login"`, `store_hash`, `customer_id`, `channel_id`, optional `redirect_to`,
`request_ip`, `enable_persistent_cart`. **TTL: `iat` valid only 30 seconds.**
"You must include the `channel_id` when using JWTs to embed checkout on a headless storefront."
"The Customer Login JWT must include a `channel_id` property. If you omit the `channel_id`, CORS checks
will fail and the checkout will not load."
— https://docs.bigcommerce.com/developer/docs/storefront/guides/customer-authentication/customer-login

**Trap — Current Customer API is unusable headlessly.** The API index classes it context "storefront",
auth "Client ID"; it "returns a BigCommerce-generated JWT signed with the client secret" but requires the
BC storefront session cookie. It is the Q5 analogue of the REST Storefront trap. Not an option for us.

**App Router split:**
- Server components: read the customer access token from cookies, attach the header, query GraphQL. Fine.
- Needs a route handler / server action: `login` and `logout` (must set/clear an httpOnly cookie),
  and minting the Customer Login JWT (needs the client secret — never in a component).
- BC's own answer: Catalyst uses **Auth.js**. "Auth.js tracks a logged-in customer's session using a JWT
  cookie." `getSessionCustomerAccessToken` retrieves it. Config in `auth/index.ts`.
  — https://docs.bigcommerce.com/developer/learn/courses/catalyst-core/expanded/customer-session

**Passwordless/OTP: UNVERIFIED.** `developer.bigcommerce.com/api-docs/storefront/passwordless-login` 301s
onto the Customer Login API page, which documents no OTP mechanism. It mentions "alternative sign-in
methods (ex. phone number and SMS password)" only as a *use case* for the JWT, with no implementation.
So: you can build OTP yourself on top of the JWT SSO (you control `customer_id`), but BC ships no
first-party passwordless flow that I could confirm.

## Options for our starter
| Option | Trade-off |
|---|---|
| **A. Auth.js with a JWT cookie holding the customer access token** ← **RECOMMENDED** | Exactly what Catalyst does, so it's the well-trodden path; handles the cookie/route-handler split for you; works with server components. |
| B. Hand-rolled httpOnly cookie + two route handlers | Fewer dependencies and fully transparent — genuinely viable since the token is just a string. Costs you CSRF and session-refresh handling you'd write yourself. |
| C. Customer impersonation tokens | Simplest server-side model, but BC says it's "less secure... being phased out". Don't build a new starter on it. |

**Pick A**, but note B is a legitimately small diff if you'd rather not take the Auth.js dependency —
the token is a single opaque string in a cookie. Reject C.

# Q6 — CHANNELS & MULTI-STOREFRONT

- **Definition:** "A channel is a place where a merchant's store sells products. Storefront websites,
  marketplaces like Amazon and eBay, point-of-sale systems, and marketing feeds are all sales channels."
- **Channel vs Site:** "every site will be tied to exactly one channel, but because not all sales channels
  are sites, channels are not required to have a site."
- Default channel `id = 1`, cannot be deleted.
- **Does a headless storefront need one? Yes.** The channels guide instructs you to "create a channel for
  your headless platform": `POST /v3/channels` → `POST /v3/channels/{id}/site` (primary domain) →
  upsert the site's checkout URL. "You need a primary domain name for your headless storefront and an
  additional domain for the storefront's checkout page." / "Subdomains are permitted."
  Caveat: "The API calls that associate domains with your store do not verify domain name ownership."
  — https://docs.bigcommerce.com/developer/docs/storefront/headless/channels
- **But you do NOT need MSF enabled for one storefront:** "When a single Catalyst storefront is needed,
  Multi-Storefront (MSF) does NOT need to be enabled." And (support): "If your store has a single headless
  storefront, you can set the default Stencil storefront as inactive, then enable your headless storefront
  as active without the necessity to purchase an additional storefront seat."
- **Catalog visibility:** "A product must be explicitly assigned to a channel to be sold on that channel."
  → **your Sanity sync must respect channel assignment or you'll publish products the channel can't sell.**
- **Currencies:** assigned per channel via Channel Currency Assignments, but "currencies must be added
  first in the Settings > Setup > Currencies settings from an active MSF-enabled BigCommerce Control Panel."
  → multi-currency per channel implies MSF enabled.
- **Tokens are channel-scoped:** `channel_id`/`channel_ids` on token creation. Private tokens **require**
  one of them. Per-channel GraphQL endpoint: `https://store-STOREHASH-CHANNELID.mybigcommerce.com/graphql`.
- **One codebase, N channels: yes.** A single token can carry `channel_ids: [1,2,3]`, and the endpoint is
  parameterised by channel ID. Routing per-channel is a config concern, not a fork.

## Options for our starter
| Option | Trade-off |
|---|---|
| **A. Single channel, `channelId` as env var, endpoint derived from it** ← **RECOMMENDED** | Ships today on any plan with no MSF purchase; the env var is the entire seam to multi-channel later. |
| B. Multi-channel from day one (channel resolved per request from host/locale) | Real multi-brand/multi-region support, but needs MSF (paid add-on, seat-capped) and complicates caching keys and ISR tags for a capability most users won't buy. |
| C. Hard-code the default channel (id 1) | Smallest diff, but strands anyone who later adds a channel and makes the token's required `channel_ids` look magic. |

**Pick A.** One env var buys B later; C saves nothing over A.

## Rate limits

| Surface | Limit |
|---|---|
| **GraphQL Storefront** | **Complexity-based, not request-count.** "complexity limit of 10,000 for each request"; query **depth limit 16**. Header `X-Bc-Graphql-Complexity`. **No per-token/per-IP request rate documented.** |
| **REST Management v3** | Core/Growth (Standard/Plus) 20k/hr = 150/30s · Scale (Pro) 60k/hr = 450/30s · Enterprise "by plan and resource" (UNVERIFIED) · Sandboxes 500k/hr |
| REST Storefront | none documented (same-origin only anyway) |
| GraphQL Admin | shares REST OAuth quota; complexity 10,000 |
| GraphQL Account | **70 requests per hour** |
| B2B GraphQL | complexity 4,500 |
| Payments API | 50 requests per 4 seconds |
| Token minting | no separate limit; consumes REST quota |

Headers: `X-Rate-Limit-Time-Window-Ms`, `X-Rate-Limit-Time-Reset-Ms`, `X-Rate-Limit-Requests-Quota`,
`X-Rate-Limit-Requests-Left`. **No `Retry-After` documented.** 429 without headers = platform overload.
https://docs.bigcommerce.com/developer/docs/overview/api-fundamentals/rate-limits

**Architectural consequence:** GraphQL Storefront is governed by *complexity per request*, REST by
*requests per 30s per store*. Putting shopper traffic on REST means every shopper shares one store-wide
quota. This is the strongest technical argument for Q3 option A.

## Webhooks (for BC → Sanity sync)

Scopes (https://docs.bigcommerce.com/developer/docs/integrations/webhooks/event-reference/events):
- Products: `store/product/*`, `/created`, `/updated`, `/deleted`, `/inventory/updated`, `/inventory/order/updated`, `store/product/metafield/*`, `store/product/variant/metafield/*`
- Categories: `store/category/*`, `/created`, `/updated`, `/deleted`, `store/category/metafield/*`
- SKUs: `store/sku/*`, `/created`, `/updated`, `/deleted`, `/inventory/updated`, `/inventory/order/updated`
- Price Lists: `store/priceList/created|updated|activated|deactivated|deleted`, record + assignment variants
- Channel-scoped: `store/channel/{id}/product/assigned|unassigned`, `store/channel/{id}/category/*`, `store/channel/{id}/categoryTree/updated`, `store/channel/{id}/settings/catalog/updated`

**Three gaps that shape the sync:**
1. **Brands have NO CRUD webhooks** — only `store/brand/metafield/*`. Poll brand renames.
2. **Variants have NO CRUD webhooks** — only variant metafields. Catch via `store/product/updated` or `store/sku/*`.
3. **Product images mostly don't fire `updated`:** "changing the current thumbnail, uploading an additional
   product image and setting it as the thumbnail, or even deleting all thumbnails, does not generate an
   update event." Poll images.

**Payload is ID-only:** `{"scope":..., "data":{"type":"product","id":250}, "hash":..., "created_at":...}`.
Always re-fetch. Each event costs a follow-up call against the REST quota.

**`hash` is NOT a signature** — "The SHA-1 hash of the JSON-encoded payload data", unkeyed. It's for
**dedup** only. For authenticity, set the optional `headers` object at creation (basic auth / shared secret;
value ≤ 8KB, name ≤ 64 chars).

**Delivery:** `POST /v3/hooks` ("None required. Create and manage webhooks with the default scope").
Retries at 60, 180, 300, 600, 900, 1800, 3600, 7200, 21600, 50400, 86400s; **after ~48h cumulative the hook
is deactivated** and an email is sent. Must return HTTP 200. Duplicates possible; **no ordering guarantee**
→ re-fetch current state, never treat webhooks as ordered deltas. Monitor `is_active` and re-arm.

**Backfill / gap recovery:** `GET /v3/catalog/products?date_modified:min=...` (also `date_last_imported`).
Pagination max 50 — **drops to 10/page when you `include` options or modifiers.**

## Versioning / deprecation — how fast does this rot

- There is a **list, not a policy**: https://docs.bigcommerce.com/developer/docs/overview/api-fundamentals/deprecations-sunsets
  **No notice period before breaking changes is stated anywhere.** Most entries carry no sunset date.
- **GraphQL Storefront is not versioned.** No version segment in the endpoint; field-level `@deprecated`
  in active use. Continuous evolution → your queries can rot silently. Pin nothing; monitor the changelog.
- **REST v2 is deprecated** (brands, categories, customers, options/option_sets, pages, products, redirects)
  with no dated sunset. Not all v2 resources have v3 counterparts yet.
- **Avoid in a new build:** `/v3/catalog/categories` (deprecated → use Catalog Trees Categories) and
  `/v3/hooks/events` (deprecated).
- Changelog: https://docs.bigcommerce.com/developer/changelog (index is client-rendered; dated entries
  resolve at `/YYYY/M/D`). **RSS/Atom feed URL UNVERIFIED** despite docs recommending "a feed alert".

**Rot rate:** moderate but real. The token s2s change landed with dates and broke the standard SSR pattern;
an unversioned GraphQL API plus no stated notice period means the changelog is your only early warning.
