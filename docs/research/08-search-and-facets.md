# Finding 08 — BigCommerce faceted search

Resolves the `UNVERIFIED` item 6 in `04-bigcommerce-api-semantics.md`. Read 2026-08-07.
Sources: BigCommerce docs (raw `.md` twins, fetched twice for cross-validation) **and** Catalyst's real
working queries. Where docs and code disagree, code wins — Catalyst's documents are generated by
gql.tada against the live introspected schema and type-checked with
`satisfies z.ZodType<RealGeneratedType>`.

## VERDICT: `filter-panel.tsx` is a **rewrite**, not an adaptation. The feature is real.

## The root field

**`site.search.searchProducts(filters: SearchProductsFiltersInput!, sort: SearchProductsSortInput)`** —
the only field that returns facets.

```graphql
# catalyst/core/app/[locale]/(default)/(faceted)/fetch-faceted-search.ts:13-24
query GetProductSearchResultsQuery(
  $first: Int $last: Int $after: String $before: String
  $filters: SearchProductsFiltersInput!
  $sort: SearchProductsSortInput
  $currencyCode: currencyCode
) {
  site { search { searchProducts(filters: $filters, sort: $sort) {
    products(first: $first, after: $after, last: $last, before: $before) { ... }
    filters { edges { node { __typename displayName ... } } }
  } } }
}
```

Ruled out: `site.products` takes `entityIds: [Int]` only, no filter argument. `site.category().products`
exists but **Catalyst deliberately bypasses it for the grid** — `category(entityId)` is called only for
metadata and breadcrumbs (`category/[slug]/page-data.ts:8-22`), while the grid comes from
`searchProducts(filters: {categoryEntityId})` (`category/[slug]/page.tsx:149-158`), because only
`searchProducts` returns facets.

## The filter input — named fields, not an opaque blob

```ts
// fetch-faceted-search.ts:279-308 — type-checked against the live schema
const SearchProductsFiltersInputSchema = z.object({
  brandEntityIds: z.array(z.number()).nullish(),
  categoryEntityId: z.number().nullish(),
  categoryEntityIds: z.array(z.number()).nullish(),
  hideOutOfStock: z.boolean().nullish(),
  isFeatured: z.boolean().nullish(),
  isFreeShipping: z.boolean().nullish(),
  price: z.object({ maxPrice: z.number().nullish(), minPrice: z.number().nullish() }).nullish(),
  productAttributes: z.array(z.object({ attribute: z.string(), values: z.array(z.string()) })).nullish(),
  rating: z.object({ maxRating: z.number().nullish(), minRating: z.number().nullish() }).nullish(),
  searchSubCategories: z.boolean().nullish(),
  searchTerm: z.string().nullish(),
}) satisfies z.ZodType<SearchProductsFiltersInput>;
```

Docs show one field Catalyst doesn't exercise: `categoryIdsFilter: { matchBehavior: AND | OR, entityIds: [Int] }`.

**Docs are wrong in two places** — they show input `isInStock: true` (the live schema has only
`hideOutOfStock`, inverted polarity, not a rename) and output field `name` (the real query uses
`displayName`). Trust the code.

## The facet output — fully structured, zero opaque strings

A `__typename`-discriminated union of six concrete types, all scalar/object fields:

```graphql
# fetch-faceted-search.ts:38-152
filters { edges { node {
  __typename displayName isCollapsedByDefault
  ... on BrandSearchFilter { brands { edges { node { entityId name isSelected productCount } } } }
  ... on CategorySearchFilter { categories { edges { node { entityId name isSelected productCount subCategories {...} } } } }
  ... on ProductAttributeSearchFilter { filterName filterKey attributes { edges { node { value isSelected productCount } } } }
  ... on RatingSearchFilter { ratings { edges { node { value isSelected productCount } } } }
  ... on PriceSearchFilter { selected { minPrice maxPrice } }
  ... on OtherSearchFilter { freeShipping {...} isFeatured {...} isInStock {...} }
} } }
```

Proof it is never opaque: `data-transformers/facets-transformer.ts` branches on `facet.__typename` at
lines 31, 60, 89, 122, 136 to build UI descriptors, and
`grep -rn "JSON.parse\|JSON.stringify"` across the whole faceted pipeline — query, transformer, filter
panel, param parser — returns **nothing**.

**Pagination caveat (new):** `brands`, `categories`, `attributes`, `ratings` and nested `subCategories`
are themselves cursor connections carrying `pageInfo` (`core/client/fragments/pagination.ts:3-10`).
Catalyst never passes `first:` on them and flattens with `removeEdgesAndNodes`, discarding
`hasNextPage`. Default page size UNVERIFIED. A brand or attribute facet with more values than that
default **silently truncates** in BigCommerce's own reference implementation. Decide whether to
paginate facet values.

## THE PLAN GATE — quoted verbatim, found on two independent pages

> "you can query facets, filter by rating, or filter by 'in-stock' only if the merchant is on a **Pro or
> Enterprise plan**."

> "A merchant must enable product filtering for facets to be returned. In addition, only facets that a
> merchant marks as visible in their Product Filtering settings will be returned." / "If a merchant has
> not enabled product filtering, you will receive an **empty array** for the returned facets, though
> products will still be returned."

Source: `docs.bigcommerce.com/developer/docs/storefront/headless/products/faceted-textual-search`

**Scope of the gate:** only the `filters` block, plus rating and in-stock filtering. Bare product search
and listing — `products`, `searchTerm`, category and brand scoping — work on any plan.

**Failure mode:** on a lower tier, `filters` returns an empty array while products keep loading. Silent
degradation, no error. The starter must render a sensible state for this, not a blank sidebar.

**Plan-name conflict, unresolved:** this page says "Pro or Enterprise". `04-bigcommerce-api-semantics.md`
sourced a 2026 rename from bigcommerce.com pricing — Standard→Core, Plus→Growth, Pro→Scale,
Enterprise→Performance. Both are plausibly true, with dev docs lagging the marketing rename. Read the
gate as **Scale or Performance** under current names, but confirm against the client's actual plan
rather than either doc.

## Predictive / typeahead — no dedicated field

No equivalent to Shopify's `predictiveSearch`. Catalyst reuses the same field with a small page:

```graphql
// components/header/_actions/search.ts:19-46
query getQuickSearchResults($filters: SearchProductsFiltersInput!, $currencyCode: currencyCode) {
  site { search { searchProducts(filters: $filters) {
    products(first: 5) { edges { node { ...SearchProductFragment } } }
  } } }
}
```

Confirmed live-as-you-type by `tests/ui/e2e/search.spec.ts:6-22`. The "categories" and "brands" groups
in the dropdown are **not** server-matched entities — they're derived by grouping the 5 returned
products' own embedded `categories`/`brand` fields
(`data-transformers/search-results-transformer.ts:34-70`).

## Shopify filter key → BigCommerce equivalent

| Shopify `Filter` key | BigCommerce |
|---|---|
| `available` | input `hideOutOfStock` / output `OtherSearchFilter.isInStock` |
| `productVendor` | `BrandSearchFilter` / input `brandEntityIds` |
| `variantOption: {name,value}` | `ProductAttributeSearchFilter` (`filterKey`) / input `productAttributes: [{attribute, values}]` |
| `category: {id}` | `CategorySearchFilter` / input `categoryEntityIds`, or `categoryIdsFilter: {matchBehavior, entityIds}` |
| `productType` | **no counterpart** |
| `tag` | **no counterpart** |

Two of six have nothing to map to. `facets-transformer.ts` is exhaustive over exactly six union members
and `OtherSearchFilter` only ever holds `freeShipping`/`isFeatured`/`isInStock` — there is no generic
passthrough bucket for arbitrary tags or product types. Remodelling them as BigCommerce custom product
attributes so they surface as `ProductAttributeSearchFilter` is plausible but **UNVERIFIED** — inference,
not sourced.

## Why rewrite and not adapt

The two APIs invert who carries filter semantics.

Shopify's `filter-panel.tsx` is generic by design: it never needs to know what `available` or
`variantOption` mean, because each value carries an opaque `input` JSON string that is `JSON.parse`d and
echoed straight back into the next query. One component handles any filter Shopify adds later, for free.

BigCommerce inverts this. The client receives a `__typename`-discriminated union and **must** branch on
it to construct a hand-typed `SearchProductsFiltersInput` with named fields per filter kind — exactly
what Catalyst's 190-line `facets-transformer.ts` switch and its `filter-parsers.ts` URL-param encoder do.
Adding a new facet kind means writing new branch code, not gaining it free.

That is a structural difference in the data-layer contract, not a rename. Scope: the query, transformer
and param-encoding layer get replaced. **The presentational shell survives largely intact** — accordion,
toggle groups, range input, star-rating checkboxes, reset button.

Two risks belong in the estimate beyond the shape call:
1. The `filters` block is commercially gated and silently returns empty on lower tiers.
2. `productType` and `tag` have no counterpart and need a merchant-catalog decision (custom attributes)
   to survive as filters at all.
